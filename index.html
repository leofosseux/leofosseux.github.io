Veille Technologique

Sécurité des applications web : bonnes pratiques & menaces actuelles

🔍

Sujet principal : Sécuriser l’authentification et les API d’une application web moderne

Je réalise une veille orientée cas réels : les attaques ciblent souvent les API et l’authentification (sessions, JWT), ainsi que les failles fréquentes du OWASP Top 10.

Mon objectif : comprendre comment les failles arrivent, leurs impacts, puis appliquer des protections côté serveur (contrôles d’accès, validation, configuration).

Fil rouge : empêcher le Broken Access Control, sécuriser sessions/JWT et réduire les risques OWASP (XSS / SQLi / CSRF).

Analyses & Sujets Étudiés

Janvier 2026
Broken Access Control (IDOR / BOLA) : la faille la plus fréquente sur les API

Le “Broken Access Control” arrive quand le serveur ne vérifie pas correctement que l’utilisateur a le droit d’accéder à une ressource. Très courant sur API : IDOR (Insecure Direct Object Reference) / BOLA (Broken Object Level Authorization).

Exemple concret :

  • API : GET /api/users/15
  • Un attaquant remplace 15 par 16 → GET /api/users/16
  • Si le serveur ne contrôle pas le propriétaire, il récupère les données d’un autre compte.

Mesures concrètes (côté serveur) :

  • ✅ Vérifier l’autorisation à chaque requête (règles “owner/admin”, RBAC/ABAC)
  • ✅ Ne jamais faire confiance aux IDs envoyés par le client
  • ✅ Journaliser les accès sensibles + alerte sur comportements suspects
API Security OWASP Accès

Mon avis : c’est la faille “simple” mais critique : tout se joue dans les contrôles d’autorisation serveur, pas dans l’interface.

Sources : OWASP Top 10 · OWASP API Security

Décembre 2025
Sessions & cookies : éviter le vol de session (session hijacking)

Une session peut être compromise si les cookies sont mal configurés, si la session dure trop longtemps, ou si l’application est exposée à XSS. L’objectif est de limiter l’exploitation en durcissant les cookies et la gestion de session.

Mesures concrètes :

  • ✅ Cookie HttpOnly (inaccessible en JS) + Secure (HTTPS)
  • ✅ SameSite=Lax ou Strict pour réduire le CSRF
  • ✅ Expiration + rotation d’identifiant de session après login
  • ✅ Invalidation de session au logout / changement de mot de passe
Auth Sessions Cookies

Mon avis : beaucoup de failles viennent de réglages “oubliés”. Les attributs de cookies sont rapides à mettre en place et très efficaces.

Sources : MDN Cookies · MDN Set-Cookie

Novembre 2025
Injection SQL : comment elle arrive et comment l’empêcher (requêtes préparées)

L’injection SQL arrive quand des entrées utilisateur sont concaténées dans une requête. L’attaquant peut modifier la requête pour lire/modifier des données. La défense la plus fiable : requêtes préparées.

Exemple concret :

  • Champ “email” non filtré → la requête est construite en concaténation
  • Un payload peut détourner la logique si l’application ne prépare pas la requête

Mesures concrètes :

  • ✅ Requêtes préparées (PDO / ORM)
  • ✅ Validation côté serveur + principe du moindre privilège côté BDD
  • ✅ Logs & monitoring sur erreurs SQL anormales
OWASP SQLi Backend

Mon avis : c’est une faille historique, mais encore présente sur de nombreux projets “petits” ou mal maintenus. Les requêtes préparées doivent être un réflexe.

Sources : OWASP SQL Injection · MDN Website security
